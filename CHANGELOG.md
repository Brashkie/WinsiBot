# Changelog

Todos los cambios notables de WinsiBot se documentan en este archivo, versión por versión, de más reciente a más antigua.

---

## [8.12.0] — 2026-10-05

**Se cierra lo que la 8.11.0 dejó a medias: el bot ya no llama a Python para nada, y lo que queda de él se compila.** La 8.11.0 bajó Python a 16 archivos y 2 routers, pero seguía habiendo tres comandos que necesitaban un intérprete —`#toanime`, `#removebg` y `#upscale`— y una API de Python entera para servirlos. Los tres están ahora en Rust, la API no existe, y Python queda en **9 archivos que son solo herramienta de consola**: `npm run monitor` y `npm run manage`. Ninguno lo arranca el bot.

Al mirar esos tres comandos de cerca resultó que **dos de los tres nunca necesitaron `torch`**: `dghs-imgutils` ya corría sus modelos con ONNX Runtime y `torch` era un `extra` suyo que este proyecto no usaba. Solo `#toanime` lo cargaba de verdad, y el mismo modelo existe exportado a ONNX: **8 MB contra 3.758 MB**, medidos en disco.

Y la otra mitad de la versión es la instalación. Antes pedía Rust instalado y ~4 minutos de `cargo build`; ahora `postinstall` baja el binario precompilado de la plataforma y verifica su SHA-256, con un workflow que compila **5 targets** al etiquetar. Las dos herramientas de consola también se compilan, con Nuitka, a ejecutables que corren **sin Python instalado**.

Buscando todo esto aparecieron **nueve bugs reales**, y dos de ellos llevaban versiones rompiendo cosas en silencio:

1. `npm run build` **nunca limpiaba `dist/`**. `tsc` compila pero no borra, y `loadCommands()` registra todo `.js` que encuentra ahí, con el último en cargarse pisando al anterior: **35 claves de comando las servía código sin fuente**. Entre ellas `#registro` y `#unreg`, eliminados a propósito en la **v8.4.1** — siete versiones resucitando una función borrada — y `#image`, que servía la versión vieja y **tapaba la migración de la búsqueda de imágenes a Rust**.
2. La **Session API de Rust no podía arrancar** siguiendo `.env.example`. El servidor leía `API_KEY` y `PORT`; el cliente y el propio ejemplo usan `SESSION_API_KEY` y `SESSION_API_URL`, y los dos primeros no estaban documentados en ninguna parte. El panic no se veía en ningún log porque `index.ts` la lanza con `stdio: 'ignore'`: solo un reintento cada 3 segundos, para siempre.
3. Los **binarios compilados no encontraban el proyecto**: `__file__` bajo Nuitka `--onefile` apunta al directorio temporal donde el binario se extrae en cada arranque, así que `manage.exe` informaba *"auth dir missing"* teniendo 8.422 archivos en `auth/`.
4. `npm run manage` **crasheaba antes de mostrar nada** en cualquier Windows con codepage heredada — cp1252, el caso por defecto en español — porque `rich` cae ahí a su renderizador legacy y lanza `UnicodeEncodeError`.
5. `start_health_monitor()` compartía un `try` entre dos servicios, así que si fallaba el import del segundo el **Health Monitor no arrancaba, en silencio**.
6. El **postinstall rompía `npm install` con un 404**: `process.exit(0)` con una petición en vuelo hacía que libuv abortara con código 127, que npm lee como postinstall fallido.
7. `npm run chaos` **mentía sobre por qué fallaba**: 8 comprobaciones reportaban *"API key inválida o faltante"* cuando la clave estaba bien y lo que faltaba era que el script leyera el `.env`.
8. `ruff` y `py:deps` excluían el **nombre exacto** `venv`, así que cualquier otro entorno al lado —un `venv.roto` de los que quedan al recrearlo, un `venv_tools`— los metía a recorrer `site-packages`: **26.165 avisos** de código que no es de este proyecto, que es lo mismo que no tener linter.
9. Y `.gitignore` tapaba solo `python/venv/`, también por nombre exacto, así que ese `venv.roto` salía como no rastreado y un `git add -A` se habría llevado **14 GB** al commit.

|------|--------|
| **Los tres comandos de imagen a Rust — y dos no necesitaban torch** | `#toanime`, `#removebg` y `#upscale` eran lo último que de verdad ataba el proyecto a Python. Al mirarlos de cerca resultó que **cada uno usa un motor distinto** y que `dghs-imgutils` ya corría sus modelos con **ONNX Runtime**: `torch` era apenas un `extra` suyo que este proyecto no usaba. O sea que solo `#toanime` lo necesitaba, por cargar AnimeGANv2 con `torch.hub`. Los tres están ahora en `vision.rs` |
| **`#toanime`: de 3,7 GB a 8 MB** | El mismo modelo —`face_paint_512_v2`— existe exportado a ONNX en `akhaliq/AnimeGANv2-ONNX`: **8 MB** contra los 3.758 MB que pesa `torch` en disco, medidos. El export tiene forma fija de 512x512 (el modelo en PyTorch era totalmente convolucional y aceptaba cualquier tamaño), así que se redimensiona, se infiere y se vuelve. El pre y post-procesado son los del original: `*2-1` a la entrada, `*0.5+0.5` a la salida. Verificado con una foto real de punta a punta |
| **`#removebg` con `ort`** | Mismo modelo `isnetis.onnx` que bajaba imgutils, misma preparación: escalar conservando la proporción, **centrar con relleno** en un cuadrado de 1024, inferir, recortar esa misma región de la máscara y volver al tamaño original. Ese encuadre es la parte fácil de equivocar —la máscara sale en coordenadas del lienzo con relleno, no de la imagen— y tiene cuatro tests propios |
| **`#upscale`: Anime4K portado, no una red** | Es el único de los tres que no es un modelo: son cinco pasos cerrados (bicúbica → luminancia al canal alfa → *push color* → Sobel → *push gradient*), de bloc97. Portado desde la implementación de referencia de `TianZerL/Anime4KPython` con sus mismos valores: 2 pasadas, fuerza de color 1/3, de gradiente 1. Sin modelo que bajar y **sin archivos temporales**: la versión de Python escribía la imagen a disco porque `pyanime4k` solo aceptaba rutas. **175 ms** contra los segundos que costaba antes |
| **Dos detalles del algoritmo que hay que respetar o el resultado cambia** | En `push_color` los cuatro bloques de dirección se evalúan **en cadena** sobre el mismo píxel, así que cada uno ve el alfa que dejó el anterior — parece un descuido del original pero no lo es. Y en `push_gradient` se **sale** en cuanto una dirección coincide, en vez de encadenar. Están comentados en el código para que nadie los "arregle" |
| **ONNX Runtime enlazado estáticamente** | El binario pasa de 10,4 a **30,9 MB** pero sigue siendo **un solo archivo**, sin DLL al lado. Es lo que resuelve Termux: el problema ahí nunca fue que faltaran binarios —las ruedas de PyPI YA son binarios— sino la libc, porque las ruedas de ARM se publican como `manylinux`, que asume glibc, y Android usa Bionic. Una librería nativa enlazada no negocia con eso |
| **Los modelos NO se incrustan, a diferencia de las personalidades** | Son 8 MB y 168 MB: quien no use estos comandos no tiene por qué cargarlos. Se bajan la primera vez y quedan cacheados en `data/models/`. La descarga va a un `.tmp` y se renombra al final, porque una descarga cortada dejaría un ONNX truncado que falla al cargar con un error que no dice nada |
| **La API de Python se fue: existía para que la vigilaran** | Tras migrar los comandos de imagen quedó con **un solo endpoint**, `GET /health`, y los únicos que lo consultaban eran `monitor.py` y `manage.py` para mostrar "FastAPI: online". Un servicio cuyo único trabajo era responder que estaba vivo. Con ella se van `python/api/` entero, `scripts/api.js`, los scripts `api` y `services` de npm, `PYTHON_API_URL`, el cliente HTTP de Python de `pythonBridge.ts` y el arranque automático desde `index.ts` |
| **`cython_ext` borrado: 6,3 MB compilando código que nadie llama** | `fast_utils.pyx` exportaba 18 funciones —parseo de comandos, rate limit, cooldowns, detección de spam, caché de grupos— **todas en Rust desde hace versiones**, y `fast_ml.pyx` otras 3 **sin un solo importador**. Lo único que alguien leía era `CYTHON_OK`, un booleano que decía "sí, compilé". Se van los `.pyx`, 1,2 MB de C generado, los `.pyd`, `npm run cython:build`, `cython:clean`, `scripts/build_cython.js` y `Cython`/`setuptools` de los requirements |
| **Python: 9 archivos, y ninguno lo lanza el bot** | De 35 archivos a **9**, todos herramienta de consola: `npm run monitor` (watchdog interactivo) y `npm run manage` (CLI de mantenimiento), más lo que usan. Se abren a mano, no corren por mensaje y nadie los arranca automáticamente. Con los comandos de imagen se fueron `torch`, `pillow`, `pyanime4k`, `dghs-imgutils`, `onnxruntime` y `opencv-contrib-python`: **más de 4 GB de dependencias por tres comandos**. `requirements.txt` pasa a ser lo que esas dos herramientas necesitan; el bot no necesita Python **para nada** |
| **`npm install` y nada más: binarios de Rust precompilados** | Compilar la Session API tardaba **~4 minutos** y pedía tener Rust instalado, que era el paso más caro de la instalación. Nuevo `scripts/fetch_rust.js` en `postinstall`: detecta la plataforma, baja el binario de la release y verifica su SHA-256. Nuevo workflow `release.yml` que compila **5 targets** al etiquetar — Windows x64, Linux x64 y ARM64, macOS Apple Silicon y **Android ARM64 (Termux)**. Nunca rompe la instalación: si no hay binario, si no hay red o si el checksum no cuadra, lo dice en una línea y compilar desde fuente sigue funcionando |
| **Termux tiene su propio target, y confundirlo da un binario que no arranca** | Android usa la libc **Bionic**, no glibc, así que su target es `aarch64-linux-android` y **no** `aarch64-unknown-linux-gnu`. Un binario del segundo baja bien y falla al ejecutarse. Está contemplado en el detector y en la matriz del workflow. Y ONNX Runtime publica build para ese target **con NNAPI**, la aceleración por hardware del teléfono, así que los comandos de imagen también funcionan ahí |
| **Los tres fallos del primer run de `release.yml`, y por qué ninguno se veía antes** | El workflow no se podía probar sin etiquetar: hasta la primera release era código no ejecutado. Al correrlo, 3 de 6 targets fallaron, por tres causas **distintas** — ninguna era la misma con tres caras |
| **Mac Intel sale de la matriz: `ort` no tiene ONNX Runtime para ese target** | `ort-sys` corta con *no prebuilt binaries available for target x86_64-apple-darwin*, y antes avisa que *can't do xcframework linking*: lo que ONNX Runtime publica para Apple es un xcframework que ya no cubre Intel. Las salidas eran compilar ONNX Runtime desde fuente en CI —decenas de minutos en cada release— o cargarlo dinámicamente, que tira abajo la premisa de **un solo archivo**. Ninguna de las dos vale la pena por una plataforma en retirada, así que el target se va y quedan **5**. Un Mac Intel instala igual: ahora `fetch_rust.js` devuelve `null` para `darwin-x64` en vez del nombre del target, así que avisa de entrada en lugar de pedir un archivo que nunca va a estar y reportar un 404, que parecería una release rota |
| **Linux ARM: faltaba el compilador de C++, no el de C** | La matriz instalaba `gcc-aarch64-linux-gnu`. Pero **ONNX Runtime es C++**, y al enlazar se pide `-lstdc++`: el build compila los 180 crates enteros y recién muere al final con `cannot find -lstdc++`, un error que en ningún momento dice que falte un paquete. Con `g++-aarch64-linux-gnu` entra también la libstdc++ de ARM, y `g++` arrastra a `gcc`, así que lo reemplaza en vez de sumarse |
| **Windows: compilaba bien y moría al firmar** | `shasum: command not found`, **después** de haber compilado los 30 MB. El paso llevaba un comentario mío que decía *"`shasum -a 256` existe en los tres runners"* — y es falso: en el Git Bash de Windows no está. `sha256sum` está en Linux y en el Git Bash de Windows pero no en macOS; `shasum` está en macOS y Linux pero no en Windows. Ninguna de las dos cubre los tres, así que ahora se prueba por orden en vez de dar una por segura. Las dos escriben el mismo formato, que es el que `fetch_rust.js` parsea |
| **Fix: el postinstall rompía `npm install` con un 404** | `scripts/fetch_rust.js` llamaba a `process.exit(0)` con una petición HTTP todavía en vuelo, y libuv abortaba con `UV_HANDLE_CLOSING` y **código 127** — que npm lee como postinstall fallido y corta la instalación entera. Y el camino del 404 es justo el más común mientras no haya release publicada. Ahora abandona lanzando y deja que el proceso termine solo |
| **Fix grave: `npm run build` nunca limpiaba `dist/`, y el bot cargaba código borrado** | `tsc` compila pero no borra: cuando un `.ts` desaparece, su `.js` se queda en `dist/` para siempre. Y `loadCommands()` hace `fast-glob('**/*.js')` sobre `dist/plugins/commands` y registra **todo lo que encuentre**, con `commandRegistry.set()` — así que el último en cargarse pisa al anterior. Había **38 archivos huérfanos**, 24 de ellos comandos, registrando 94 claves de las que **83 chocaban con comandos vivos**. Resultado medido: **35 claves las servía código sin fuente** |
| **Lo que eso provocaba, en concreto** | `#registro` y `#unreg` **seguían funcionando**, pese a haberse eliminado a propósito en la **v8.4.1** — siete versiones resucitando una función borrada. `#image`/`#imagen`/`#img`/`#buscarimg` los servía `util/imagen.js`, la versión vieja, que tapaba a `util/image.ts`: **la migración de la búsqueda de imágenes a Rust no estaba surtiendo efecto**. Lo mismo con `#insult`, `#gift`, `#convert`, `#cofre`, `#memepe` y `#minarexp`, todos atendidos por los nombres en español de antes del renombrado a inglés |
| **Arreglado en las dos puntas** | `npm run build` pasa a ser `rimraf dist && tsc && tsc-alias`, así que no puede volver a pasar. Verificado después: **271 `.ts` → 271 `.js`, cero huérfanos y cero claves ganadas por código sin fuente** (antes: 309 `.js` para 271 `.ts`). El alcance era solo los comandos: los middlewares y los eventos se importan por nombre, no con un glob, y el panel web usa Vite, que sí limpia su salida |
| **Fix grave: la Session API de Rust no podía arrancar siguiendo `.env.example`** | El servidor leía `API_KEY` y `PORT`. El cliente de TypeScript usa `SESSION_API_KEY` y `SESSION_API_URL`, y `.env.example` documenta **esos dos y ninguno de los primeros**. O sea que quien clonara el repo y copiara el ejemplo se encontraba con que la API **no arrancaba**: panic en `config.rs` al cargar la configuración. Y no se veía en ningún log, porque `index.ts` la lanza con `stdio: 'ignore'` — solo un reintento cada 3 segundos, para siempre. Encontrado al intentar levantarla para correr `chaos` contra ella. Ahora el nombre canónico es `SESSION_API_KEY` (con `API_KEY` como respaldo para no romper a quien lo tenía), y el puerto sale de `SESSION_API_URL` si no hay `SESSION_API_PORT`/`PORT`: se declara **una vez** y no hay forma de que cliente y servidor queden en puertos distintos, que es lo que pasaba — URL en 18080, servidor escuchando en 3001. Con 4 tests para el parseo del puerto |
| **Primera prueba de Nuitka: funciona, pero no resuelve lo que parecía** | Se probó con un script de 10 líneas que usa `rich`: salió un binario de **12,9 MB** que corre sin Python instalado, en **~17 minutos**. Lo que la prueba dejó claro es qué NO arregla — hay que compilar **por plataforma**, y para Termux habría que compilarlo *en* Termux, donde hacen falta Python y un compilador, o sea que el requisito vuelve movido de sitio. Y que **`rich` es Python puro**: 77 módulos, 916 KB de fuente, **cero binarios nativos**, así que no existe un `.so` suyo que bajar — si se quiere un binario, hay que compilarlo |
| **`npm run tools:build`: las herramientas de consola, compiladas** | Nuevo script que pasa `monitor` y `manage` por **Nuitka** y produce ejecutables que corren **sin Python instalado**, `rich` incluido. Medido por el camino real (`npm run tools:build` con el venv del proyecto): **monitor 16,0 MB en 3,1 min** y **manage 16,1 MB en 3,0 min**. La primera vez son del orden de 15-20 minutos por herramienta, que es cuando Nuitka baja su backend de C. `nuitka` entra en `requirements-dev.txt`, y si no está el script lo dice con el comando exacto para instalarlo en vez de fallar a medias |
| **Qué se deja fuera al compilar, y qué se pierde con eso** | `--nofollow-import-to` para `numpy`, `scipy`, `sklearn`, `joblib`, `pandas` y `matplotlib`. Las usa el detector de anomalías de `ai_brain.py` (IsolationForest) y son **811 MB de fuente** entre numpy, scikit-learn y joblib: incluirlas multiplicaría el binario por diez. Lo que se pierde, dicho claro, es **ese detector**: `monitor.exe` arranca el Health Monitor y lo demás, y del AI Brain informa `no disponible: No module named 'numpy'`. El resto del watchdog funciona igual |
| **Fix: los binarios compilados no encontraban el proyecto** | Los 8 sitios que calculaban la raíz lo hacían con `Path(__file__).parent.parent.parent`. Compilado con Nuitka `--onefile` eso **no sirve**: `__file__` apunta al directorio temporal donde el binario se extrae a sí mismo en cada arranque, un sitio que se borra al salir y donde no hay ni `.env`, ni `auth/`, ni `data/`. Se veía: `manage.exe status` informaba *"auth dir missing"* teniendo **8.422 archivos** en `auth/`, y mostraba el puerto por defecto en vez del del `.env`. Las dos pistas habituales no valen —`sys.frozen` es **False** bajo Nuitka, y `sys.executable` también apunta al temporal—; la que sí apunta al ejecutable de verdad es `__compiled__.containing_dir`, que Nuitka inyecta en **todos** los módulos compilados y no solo en el principal. Nuevo `python/paths.py` con los dos casos y un `WINSIBOT_ROOT` por si alguien mueve el binario. Verificado: el `.exe` lee el puerto del `.env` y encuentra `auth/` desde cualquier directorio |
| **Fix: `npm run manage` crasheaba en cualquier Windows en español** | `rich`, cuando la consola arranca con una codepage heredada —cp1252, el caso por defecto— cae a su renderizador legacy y lanza `UnicodeEncodeError` al escribir el primero de sus símbolos: la herramienta moría **antes de mostrar nada**. No era cosa de Nuitka, la versión interpretada hacía lo mismo; solo que a mano uno puede taparlo con `PYTHONUTF8=1` en el entorno y compilado no, porque Nuitka no tiene una opción para eso. Las dos herramientas reconfiguran ahora su salida a UTF-8 con `errors='replace'` antes de crear la `Console`, que es donde `rich` decide cómo renderiza |
| **Fix: el Health Monitor podía no arrancar nunca, en silencio** | `start_health_monitor()` importaba `ai.health_monitor` y `ai.ai_brain` en el **mismo** `try`, y arrancaba el primero DESPUÉS del segundo import. Si `ai_brain` fallaba —por un modelo corrupto, por numpy ausente, por lo que fuera— la excepción saltaba antes de `start_background(interval=30)` y el Health Monitor **no se iniciaba**, sin que nadie se enterara. Son dos servicios distintos y ahora cada uno tiene su propio `try/except`. Se vio en vivo al correr el binario compilado, donde numpy está excluido a propósito: `Health Monitor iniciado` y, en la línea siguiente, `AI Brain no disponible` |
| **No va al workflow de release, y es a propósito** | Nuitka **no cruza plataformas**: el binario que sale sirve para la máquina donde se compiló. Para tener uno de Termux habría que compilarlo *en* Termux, donde hacen falta Python y un compilador — o sea que el requisito que se quería quitar vuelve, movido de sitio. Y estas dos herramientas son del operador: quien instala el bot **nunca las ejecuta**. Compilarlas en CI triplicaría el tiempo de publicación para no cambiarle nada a quien instala, así que queda como un paso manual |
| **Fix: `npm run chaos` mentía sobre por qué fallaba** | Las 8 comprobaciones del escenario 9 que hablan con la API fallaban todas con *"API key inválida o faltante"*, que suena a clave mal configurada. La clave estaba bien: el script leía `process.env.SESSION_API_KEY` y **nadie la había puesto ahí**, porque está en el `.env` y `chaos.js` no lo cargaba. Un `import 'dotenv/config'` al principio. **35/35 sin exportar nada a mano** |
| **`py:deps` y `ruff` se metían a lintear el entorno virtual** | Los dos excluían el nombre exacto `venv`, así que un `venv.roto` de los que quedan al recrear el entorno —o un `venv_tools` aparte— entraba al recorrido completo: `ruff` sacaba **26.165 avisos** de código que no es de este proyecto, que es lo mismo que no tener linter, y `py:deps` reportaba `pandas`, `celery` y `polars` como imports del bot. Un entorno virtual se reconoce por tener `pyvenv.cfg`, que es lo que lo define, así que ya no hace falta acertar el nombre; en `ruff.toml` queda como `venv*`/`.venv*` |
| **`py:deps`: dos excepciones que tapaban nombres inexistentes** | Su lista de "declarado a propósito aunque nadie lo importe" llevaba `onnxruntime` y `opencv-contrib-python`, que eran runtime de `dghs-imgutils`. Las dos se fueron de los requirements al pasar los comandos de imagen a Rust, así que la excepción seguía ahí cubriendo paquetes que ya no se declaran. Quedan `ruff` y `nuitka`, que se invocan con `python -m` y no se importan nunca. Y la lista de módulos propios, que estaba a mano y seguía nombrando `api`, `routers` y `middleware`, se lee del disco contando las dos formas que Python reconoce: directorio (paquete) y `.py` suelto (módulo) — sin eso, `paths.py` salía reportado como un paquete de PyPI sin declarar |
| **Documentado: un venv hay que recrearlo al actualizar Python** | Un entorno virtual guarda la **ruta absoluta** del intérprete que lo creó, y sus extensiones compiladas llevan la versión en el nombre (`cp311`), así que no se puede reapuntar a otra. Si ese Python desaparece —al actualizarlo, o al traerse el repo de otra máquina— `py:lint`, `py:deps`, `tools:build`, `monitor` y `manage` fallan **todos** con `No Python at '...'`, porque los cinco pasan por `venvPythonPath()`. Pasó de verdad acá: el venv apuntaba a un `C:\Users\User\...\Python311` de otro perfil, con 14 GB de paquetes que ya no se usan. No es un bug del proyecto, pero no estaba escrito en ninguna parte y el síntoma no dice qué hacer, así que va en los dos README junto a los comandos para recrearlo. Verificado con Python 3.14: los 7 paquetes más `ruff` instalan con rueda `cp314`, sin compilar nada |
| **Fix encontrado al recrear el entorno: `.gitignore` solo tapaba `python/venv/`** | El patrón era el nombre exacto, así que el `python/venv.roto` que queda al recrear el entorno salía como **no rastreado** — y un `git add -A` se habría llevado **14 GB** de site-packages al commit. Pasa a `python/venv*/` y `python/.venv*/`. Es el mismo error de forma que tenían `ruff.toml` y `py_deps.js`: tres sitios distintos dando por supuesto que un entorno virtual se llama `venv` |
| **`.gitignore` repasado entero, y dos patrones anchos documentados** | Borradas las reglas muertas: la sección de `php/` (PHP se fue en la **8.8.1**), las tres de `python/cython_ext/*` (borrado en esta versión) y los `eggs/`, `parts/`, `var/`, `sdist/`, `wheels/` del template de setuptools, que no coinciden con nada desde que Python no compila nada — `build/` queda acotado a `python/build/`, porque desnudo taparía en silencio la salida de cualquier build futuro. Y los dos que SÍ son anchos a propósito quedan explicados en el archivo, porque estrecharlos rompe cosas: **`bin/`** tapa los **305 MB de ffmpeg** que hay en la raíz (acotarlo a `python/bin/` los subiría), y **`data/`** no está anclado para tapar también `rust/data/` — que es lo que costó una vez, cuando los JSON de personalidades se pusieron ahí y no se habrían subido, con el build fallando en cualquier clon. De paso: un `!data/.gitkeep` sería un no-op, porque git no desciende a un directorio ignorado |

1. La tabla `conversations` **no tenía ni un índice**, y se recorría entera en cada respuesta de IA.
2. `/ml/predict/spam` **borraba mensajes legítimos**: no era un clasificador de contenido sino un rate limiter al que se le pasaba un remitente fijo, así que todos los usuarios de todos los grupos compartían un contador de 8 mensajes cada 5 segundos — y al noveno, el bot borraba el mensaje y acusaba públicamente a quien lo escribió.

| **Circuit breakers en las dependencias externas** | Cuando Python o Rust se caen, seguir llamándolos cuesta el timeout completo por intento — y las dos están en el camino crítico: el middleware de rate limit llama a Python en CADA comando y el handler llama a Rust en CADA mensaje, así que con una de las dos caída todos los mensajes esperan el timeout (más el reintento de `axios-retry`) para acabar fallando igual, ocupando mientras tanto un slot del semáforo de `handler.ts`. Nuevo `lib/circuitBreaker.ts` con el ciclo clásico: tras N fallos seguidos el circuito se abre y las llamadas fallan al instante sin tocar la red; pasado el tiempo de espera deja pasar **una** de prueba (half-open) y si responde vuelve a cerrarse. Medido con Python caída: de **242 ms a 0.01 ms** por llamada una vez abierto, manteniendo la misma forma de respuesta (`{success:false}`) para que nada aguas arriba cambie. Un circuito por dependencia — que Python esté caída no corta las llamadas a Rust |
| **Lo que NO cuenta como fallo, que es la parte delicada** | Un 4xx significa que la petición estaba mal, no que el servicio se cayó: contarlo abriría el circuito por un bug propio y dejaría sin IA a todo el bot. El caso concreto es `/rate/check` de Rust, que devuelve **429 a propósito** cuando bloquea a alguien (ya documentado en `allowNon2xx`, `lib/session.ts`) — contarlo abriría el circuito justo cuando el rate limiter está funcionando bien, y dejaría de filtrar spam. Lo que mide el circuito es si el servicio **contesta**, no si nos gustó la respuesta: solo cuentan timeouts, conexión rechazada y 5xx. Verificado con 20 respuestas 429 seguidas (circuito cerrado) contra 10 llamadas a un puerto muerto (circuito abierto) |
| **Dead-letter queue** | `retry_count` se incrementa **antes** de cada reintento, no después: si el envío cuelga o el proceso muere ahí, en el próximo arranque el contador ya subió. Pasados 3 intentos el mensaje sale del listado de `unsent` —se acabó el reintento infinito que quema CPU— pero **no se borra**: sigue en la base con su contenido para inspeccionarlo, reprocesarlo o descartarlo a mano |
| **Fix: el mismo mensaje podía ejecutarse dos veces** | `socket.ts` acepta `type === 'append'` —mensajes que Baileys re-entrega después de un sync, filtrados solo por antigüedad (<5 min)— y el buffer interno de eventos de Baileys se activa en **cada** reconexión, no solo al arrancar (lo dice el propio comentario de `messages.upsert`), y las reconexiones por Bad MAC son habituales en grupos activos. No existía **ninguna** protección por id de mensaje: un `#daily` seguido de una reconexión dentro de esa ventana se ejecutaba dos veces — dinero duplicado, cooldown pisado, XP doble. Nuevo `core/dedup.ts` con dos decisiones que importan: el registro va **en disco** (un `Set` en memoria se pierde justo en el escenario del reinicio, que es cuando Baileys re-entrega en el sync del arranque) y está separado **por instancia** — los ids de mensaje son globales de WhatsApp, así que un mensaje en un grupo donde están el bot principal y un sub-bot llega a los dos: con un espacio de claves compartido, el segundo en llegar lo habría visto como duplicado y habría dejado de responder. Cuesta 60 µs por mensaje nuevo y 0.68 µs por duplicado, contra los 1–3 ms que el bot ya paga por mensaje en `checkRate` (Rust) y `/spam/check` (Python). Loguea cada 30 min cuántos duplicados descartó, para saber con qué frecuencia estaba pasando de verdad |
| **DuckDB eliminado — `conversations.rs` y `bad_mac.rs` a `rusqlite`** | El crate `duckdb` con `features = ["bundled"]` compila toda la librería DuckDB en C++ desde cero: es lo que el propio README documentaba como *"10–30+ min en un teléfono"*, y en esta máquina ya ni terminaba (`libduckdb-sys: ToolExecError` contra `cl.exe` de MSVC 14.51 — el `.exe` en `target/release` era de una compilación vieja). Lo usaban solo dos cosas, y ninguna analítica: un **contador** de eventos Bad MAC y un log de conversaciones de la IA. La API de `duckdb` y la de `rusqlite` son casi idénticas (`Connection`, `params!`, `query_row`, `query_map`, `execute_batch`), así que la migración fue mecánica; solo cambió el esquema: `gen_random_uuid()` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `DOUBLE` → `REAL`, `BOOLEAN/false` → `INTEGER/0`. Medido: `cargo check` de **fallar** a 15 s, y un build de release limpio a **3 m 19 s**. Sin riesgo de datos: no existía ningún `.duckdb` en `data/`. De paso, `rust/build.rs` (enlazaba `rstrtmgr.lib`, que DuckDB necesita en Windows para el Restart Manager) se va entero |
| **Y de paso arregla un bug que el propio código documentaba** | El comentario de `bad_mac.rs` explicaba que DuckDB es single-writer por archivo, y que por eso `bad_mac_events` *"nunca se creó de verdad — cada intento de persistir un clear fallaba en silencio con Catalog Error"*. La conexión de conversaciones ahora abre con `journal_mode = WAL` y `synchronous = NORMAL` (mismo criterio que `db.rs`): SQLite en WAL admite lectores concurrentes mientras hay un escritor, que es justo lo que DuckDB no daba |
| **Fix: el respaldo de credenciales perdía su última escritura al apagar** | `sessionClient.save()` encola las creds con un debounce de 5 s para no saturar a Rust con una escritura por mensaje, y su propio doc-comment decía *"Llama flushNow() antes de salir para asegurar la última escritura"* — pero `flushNow()` no lo llamaba **nadie**. El respaldo en Rust quedaba hasta 5 segundos por detrás del disco, y ese respaldo es exactamente el que lee `authVerifier.readBackup()` para recuperar cuando la sesión principal está corrupta: el momento en que más importa que esté al día. Conectado a `shutdownCleanly()` y a SIGTERM, con dos detalles que había que acertar: va **antes** de `killSpawnedChildren()` (escribe por HTTP contra Rust, y esa función mata justamente ese proceso), y con un techo de 2 s, porque `/write` hace un `fsync()` real y el supervisor manda SIGKILL a los 5 s — quedarse esperando el flush arriesgaría perder también `saveAll()`, que importa más |
| **Código muerto: 9 rutas de Rust** | `/ai/export`, `/badmac/export`, `/badmac/reset`, `/badmac/stats`, `/rate/stats`, `/audit`, `/snapshots`, `/messages/stats` y `/messages/cleanup` — ninguna tenía un solo llamador en TypeScript, Python ni en el panel web. Con ellas se van sus handlers, los métodos `reset`/`stats`/`global_stats` del tracker de Bad MAC, `tracked_count` del rate limiter, tres structs de query params con sus funciones `default_*`, `db::get_audit`, `AuditEntry`, `snapshot::list` y el import `routing::delete`. **Rust compila sin un solo warning.** Se conservan a propósito `/messages/pending` (núcleo del outbox que falta activar) y `db::audit_log`, que sigue escribiendo aunque ya no haya endpoint para leerlo — la tabla se consulta con `sqlite3` a mano |
| **Código muerto: 3 routers de Python y 5 métodos del cliente TS** | Fuera `routers/groups.py`, `routers/ratelimit.py` y `routers/cache.py`, sin una sola llamada desde el bot. En `lib/session.ts`, fuera `isHealthy`, `snapshots`, `resetBadMac`, `getDeliveryStats`, `cleanupMessages` y el tipo `DeliveryStats` — de 352 a 306 líneas |
| **Nota sobre la auditoría** | Dos endpoints se dieron por muertos y **no lo estaban**: `/sessions/backup` lo usa `authVerifier.ts`, y `health()`/`recover()` los llama `ensureHealthy()` dentro del propio `session.ts`. Este script es la vía para inspeccionar el padrón, sacar un respaldo legible y restaurar desde uno — incluido `users.json.migrated`. `import` avisa de que el bot tiene que estar parado (dos procesos sobre el mismo log lo corromperían) y pide confirmación |

| **Medido y descartado (queda documentado para no volver a intentarlo)** | **`strenor` como caché en memoria:** es entre 25× y 430× más lento que un `Map` porque cruza el puente NAPI y serializa JSON en cada operación — 64.70 µs contra 0.15 µs por `get` de un `groupMetadata` de 200 participantes, que se consulta en el camino crítico de cada mensaje de grupo. Peor aún, el viaje por JSON destruye datos: `undefined` desaparece, `Date` se vuelve `string`, `Buffer`/`Set`/`Map` se rompen, y cada `get` devuelve un objeto nuevo — eso rompería el `history.push(...)` de `gpt.ts`, que muta el array cacheado en el sitio. `strenor` está bien donde dice estar (su README se compara con `better-sqlite3`, no con un `Map`): persistencia embebida, no caché caliente. **BLAKE3 para la detección de cambios:** más lento que sha1 aquí (10.1 ms contra 8.0 ms para los 2557 usuarios) — con miles de entradas de ~870 bytes domina el cruce del puente NAPI, no el hashing; BLAKE3 gana en entradas grandes, no en muchas pequeñas |

| **Rust — I/O bloqueante movida fuera del runtime async** | Los handlers de sesión (`write`, `read`, `is_healthy`, `list_sessions`, `health`, `readiness`, `snapshot_route`, `recover`, `list_snapshots`, `read_backup`, `sessions/signal/clear`) hacían lectura/escritura de archivos síncrona directo en funciones `async` de Tokio — bloqueando el hilo del runtime para *cualquier otra petición* concurrente mientras tanto. El más grave: `write` (guardado de credenciales, se dispara en cada `creds.update` de Baileys de cada bot y sub-bot) incluye un `fsync()` real. Todos movidos a `tokio::task::spawn_blocking`, mismo patrón que ya usaban los endpoints de mensajería |
| **`bad_mac.rs` — algoritmo de ventana deslizante real** | El contador de Bad MAC por grupo usaba bloques fijos de tiempo (tumbling window) que se resetean enteros cada 30s — una ráfaga repartida justo alrededor del límite de un bloque (4 eventos a los 29s + 4 a los 31s) nunca cruzaba el umbral de 5 en ninguno de los dos bloques, aunque fueran 8 eventos reales en 2 segundos. Reemplazado por un log de timestamps con purga incremental (sliding window log real), sin ese punto ciego y sin costo extra (O(1) amortizado por evento) |
| **`bad_mac.rs` — fuga de memoria corregida** | El mapa de contadores por grupo nunca se limpiaba — cualquier grupo que tuvo aunque sea un Bad MAC suelto quedaba en memoria para siempre. Nueva tarea de fondo (cada 30 min) libera grupos inactivos por más de 1h que nunca dispararon una limpieza real; los que sí reincidieron se mantienen indefinidamente para no perder su escalada de cooldown |
| **Rate limiting — Rust nunca bloqueaba de verdad** | `/rate/check` de Rust devuelve HTTP 429 a propósito cuando bloquea a alguien, pero el cliente TS trataba cualquier respuesta no-2xx como "Rust caído" y caía a su fallback de "permitir siempre" — el límite de 15 msj/10s de Rust nunca bloqueaba a nadie en la práctica |
| **Rate limiting — el límite local era más estricto que el real y silencioso** | Un segundo límite en memoria (5 mensajes/5s, en TODO mensaje) bloqueaba antes que el de Rust y solo avisaba 1 de cada 3 veces — las otras 2, silencio total. Subido a 12/5s, como red de respaldo real en vez de ser el que más rápido se disparaba con uso normal |
| **`authVerifier` — menos falsos positivos en cada reconexión** | El verificador de integridad de `auth/` corría su barrido completo (todos los `session-*.json`) en cada reconexión, no solo al arrancar — exponiendo cientos de archivos a glitches de I/O transitorios en cada una. Ahora solo corre en el arranque en frío del proceso, y reintenta una vez antes de dar un archivo por corrupto |
| **`#mcsearch`/`#mcfriends`/`#mcachievement` reparados** | La API de OpenXBL anida los resultados bajo `content.people`/`content.titles`, no directo como se leía — por eso nunca encontraba jugadores reales. También corregidos dos nombres de campo mal escritos (`gamerScore`, `totalGamerscore`) que dejaban el gamerscore siempre en "N/D" |
