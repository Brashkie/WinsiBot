# Changelog

Todos los cambios notables de WinsiBot se documentan en este archivo, versión por versión, de más reciente a más antigua.

---

## [8.8.0] — 2026-07-28

Quinta ronda, la más grande hasta ahora: el bot pasa a ser realmente multiplataforma (Linux/macOS/Android vía Termux, no solo Windows), el branding (nombre, canal) se vuelve configurable por instancia en vez de estar hardcodeado como "WinsiBot", se quitó el límite artificial de "10,000 grupos" del marketing, y la sesión de WhatsApp pasa de JSON a CBOR de punta a punta (TS + Python + Rust) — más compacta, más rápida, sin perder ninguna herramienta de diagnóstico/recuperación existente. Además: sub-bots con nombre y medios propios, `#menu` rediseñado para listar comandos reales, limpieza de 9 archivos muertos, y un módulo nuevo en Rust que detecta e informa la plataforma en la que corre.

| Área | Cambio |
|------|--------|
| **Multiplataforma de verdad — Linux, macOS, Android (Termux)** | No era un port desde cero: `start.sh` y algunos scripts ya brancheaban bien por SO, pero 8 scripts más nuevos (`celery`, `health`, `monitor`, `api`, `spam:build`, `py:lint`, `py:format`, `manage`) tenían `python/venv/Scripts/python.exe` hardcodeado sin ninguna rama para Unix — no arrancaban fuera de Windows. Nuevo `src/lib/platform.ts` + `scripts/_platform.js` centralizan la resolución de rutas/binarios por SO en un solo lugar |
| **Fix real (no cosmético): el filtro nativo de spam/flood se desactivaba en silencio fuera de Windows** | `spam_guard.py` solo buscaba `spam_guard.dll` — en Linux/macOS `ctypes.CDLL` fallaba y el chequeo rápido caía a `{'allowed': True}` sin avisar nada, es decir, dejaba de filtrar CUALQUIER cosa sin que se notara. El código C ya tenía soporte multiplataforma (`#ifdef _WIN32`) pero el script de build y el loader de Python no. Ahora elige `.dll`/`.so`/`.dylib` según el SO real, con un `build_cython.js` unificado que reemplaza tanto el `.ps1` (Windows) como el `.sh` (POSIX, nunca conectado a ningún script de npm) |
| **Branding configurable — el nombre y canal ya no están hardcodeados** | "WinsiBot" estaba escrito a mano en ~20 archivos (headers HTTP, mensajes, sticker packs, el nombre del sub-bot en WhatsApp). Ahora sale de `config.botName` (`.env`: `BOT_NAME`), y el canal de "Ver más" del menú sale de `NEWSLETTER_JID` (opcional — si no se configura, simplemente no se arma ese contexto). La línea de crédito ("Hepein Oficial x Brashkie") se mantiene fija a propósito, vía `CREDIT_LINE` — es la única parte que no cambia aunque cambies el nombre del bot |
| **Fix: 3 comandos +18 leían mal `config.botName` por una variable tapada** | `sexyimg.ts`/`porngif.ts`/`stickerporn.ts` ya tenían una variable local `config` (la configuración del GRUPO, no la del bot) que tapaba el `config` importado — al ponerle `config.botName` en el header HTTP, en realidad leía el objeto equivocado. Encontrado y corregido en el mismo barrido de branding |
| **Sin límite artificial de grupos** | El README afirmaba "10,000+ grupos" sin que existiera ningún contador de grupos en el código — reescrito con lenguaje honesto. De paso, `MAX_CONTACTS` (rotación de caché de contactos) pasa de constante fija a configurable por `.env` |
| **Limpieza — 9 archivos muertos y 2 exports sin uso** | Borrados `scheduler.ts`, `scraper.ts`, `notifications.ts`, `globals.ts`, `logCapture.ts`, `media.ts`, `ezgif.ts`, `safeMessage.ts` (cero importadores reales, verificado por grafo de imports) y `core/queue.ts` (vacío). Quitados `banUser`/`isBanned` de `security.ts` y `forceJid`/`sendMention` de `jid_utils.ts` (sin un solo llamador). `CATEGORY_SYMBOLS`, que vivía duplicado en `menu.ts` y `category.ts`, ahora es un único archivo compartido |
| **Sub-bots con nombre y medios propios** | Nuevo `#serbot setname <nombre>` (sobrescribe el nombre de perfil de WhatsApp que se mostraba antes) y `#serbot setmedia <clave>` (respondiendo a una imagen/video — guarda un medio propio para ESE sub-bot, por ejemplo su propio `#menu`). Si un sub-bot no tiene un medio propio, sigue cayendo al compartido de siempre — cero cambio de comportamiento para el bot principal |
| **`#menu` rediseñado — lista comandos reales, no solo conteos** | Antes mostraba "categoría — N comandos" nada más. Ahora RPG y Roleplay se listan completas siempre (nombre + descripción, como ya hacía `#categoria`), el resto se resume por categoría salvo que pidas `#menu todo` (listado completo). `#categoria <nombre>` sigue igual para ver una sola categoría |
| **Sesión de WhatsApp: JSON → CBOR, de punta a punta** | `creds.json`/`session-*.json`/`sender-key-*.json` etc. pasan a guardarse en CBOR (binario nativo, sin el ~33% de inflado que mete `base64` para los bytes de las claves Signal) — migración automática, sin downtime, cada archivo pasa a `.cbor` la primera vez que se toca. Extendido a **todo** lo que ya sabía leer sesión en JSON para no perder cobertura: el verificador de integridad Curve25519 (`authVerifier.ts`), `#clearsession`/`#backup`, reconexión de sub-bots, y del lado de Python `session/manager.py` (health/backup/restore/checksums), `manage.py`, `health_monitor.py` — más el endpoint de limpieza de Bad MAC en Rust, que sin este fix hubiera dejado de borrar nada silenciosamente. Verificado con una copia real de la sesión en vivo, no solo con datos de prueba |
| **Rust — nuevo módulo de detección de plataforma** | `platform.rs` reporta SO/arquitectura/núcleos al arrancar y en `/health` — mismo criterio que ya tenía el lado de Node (`platform.ts`), pensado para cuando esto corra en varios servidores y haga falta saber qué máquina es cada instancia sin entrar a mano |
| **Fix: `_platform.js` y `platform.ts` ya se habían desincronizado** | El JS plano (para scripts que corren sin `tsc`) le faltaban `IS_MAC`/`IS_LINUX` que el TS sí tenía — no se podía usar directo porque no pueden importarse entre sí (fronteras de build distintas), así que ahora hay un test (`scripts/_platform.test.js`) que falla si vuelven a desincronizarse |

## [8.7.0] — 2026-07-28

Cuarta ronda: cada configuración de grupo pasó a ser su propio comando (30 en total, con tarjeta de instrucciones + estado), se auditó el registro completo de comandos y se encontraron y corrigieron 12 bugs reales de comandos silenciosamente rotos (colisiones de nombre/alias, `#ban` sin efecto, cooldowns cruzados), más una ronda de rendimiento en Python (6 endpoints bloqueando toda la API) y consola (menos trabajo síncrono por mensaje).

| Área | Cambio |
|------|--------|
| **Cada configuración de grupo pasó a ser su propio comando** | Las ~30 opciones de `#on`/`#off` (antilink, antispam, welcome, nsfw, etc.) ahora tienen cada una su propio comando (`#antilink`, `#antispam`, `#welcome`...) con `enable`/`disable` como argumento, y sin argumento muestran una tarjeta con instrucciones + estado actual (❐ explicación · ✎ cómo activar/desactivar · ✦ estado). `#on`/`#off` sigue funcionando igual que antes como panel general — ahora rediseñado al mismo lenguaje visual (✔/✗/✦/❐/✎), reemplazando el `╭─「 」` viejo y los ❌ sueltos que quedaban. De paso se corrigió un bug real: `#antilink` y `#mute` standalone escribían su configuración en un store de Python que la moderación real NUNCA leía — el toggle "funcionaba" (respondía "activado") pero no hacía nada. Ahora los 30 comparten la misma fuente de verdad (`groupConfigs`) que ya usa `#on`/`#off` y los handlers de moderación reales. Toda la metadata vive en un solo módulo compartido (`@lib/groupToggles.ts`) |
| **Fix: `#ban` no baneaba a nadie de verdad** | Mismo bug que `#antilink`/`#mute`: escribía en el store de Python (`pythonPost('/api/v1/users/.../ban')`) que nadie lee — la moderación real chequea `user.banned` en `handler.ts`, que vive en el store de TS (`getUserData`). El comando decía "usuario baneado" pero la persona baneada seguía usando el bot con total normalidad. Reescrito para usar el store real, mismo patrón que ya usaba `#unban` correctamente — de paso ahora acepta un motivo (`!ban @usuario razón`) que se muestra cuando la persona baneada intenta usar el bot |
| **Fix: 10 comandos rotos por colisión silenciosa de nombre/alias** | El registro de comandos es un `Map` plano — si dos archivos registran el mismo nombre o alias, el que carga después pisa al primero SIN aviso. Auditado el registro completo (634 nombres+alias): 10 colisiones reales, todas comandos distintos que compartían una palabra por accidente. Las más notorias: `!info` (esperabas la ficha pública del bot) abría el panel de owner `sysinfo` en su lugar; `!stats` (estadísticas del bot) abría tu perfil RPG; `!regalo` — usado en el propio texto de ayuda de `#gift` — en realidad reclamaba el `!daily`; `!trade` (intercambiar personajes) apostaba en el mercado. Corregido quitando el alias de más en cada par — las 10 funciones vuelven a responder a su propio nombre |
| **Fix: `#invertir` y `#roulette` compartían el mismo cooldown por error** | Los dos comandos usaban la misma clave interna (`lastBet`) para cooldowns completamente independientes (10s vs 15s, mensajes distintos) — usar uno bloqueaba el otro con un "espera" falso aunque nunca lo hubieras usado. `#roulette` ahora tiene su propia clave (`lastRoulette`). De paso, `#einfo` (panel de cooldowns) tenía las duraciones de `Slut`/`Crime` hardcodeadas por separado y habían quedado desactualizadas tras el cambio de cooldown de la 8.6.0 (mostraba 1h en vez de 10/15 min reales) — corregido, y sumadas las filas de Invertir/Roulette que faltaban ahí |
| **Fix: `#menu` y el log de arranque contaban alias como comandos aparte** | `commandRegistry` guarda una entrada por cada alias además del nombre real (para resolver `#s` y `#sticker` al mismo comando) — `#menu` y el log de arranque iteraban el registro completo sin deduplicar, así que un comando con 3 alias se contaba como 4. `#infobot`/`#categoria` ya lo hacían bien; ahora los cuatro cuentan comandos ORIGINALES únicos por igual. Total real: 191 (incluye `#bots`/`#settier` y las 28 configuraciones de grupo convertidas en comando propio) |
| **Nuevo: `#bots` — resumen de sub-bots por categoría** | `#serbot lista` ya existía pero lista uno por uno — inmanejable a cientos/miles de sesiones. `#bots` muestra el total y un resumen por categoría (Principal/VIP/Premium/Pro/Pro Max/Free) más qué sub-bot está activo en el grupo actual. Las categorías por ahora son solo una etiqueta (`#settier`, nuevo comando de owner) — no cambian ningún beneficio de juego, el `premium` existente sigue siendo el que gatea eso |
| **Limpieza: función de extraer número de JID duplicada 16 veces en 11 archivos** | El mismo `.replace('@s.whatsapp.net','').replace('@lid','').replace(/[^0-9]/g,'')` estaba reescrito inline en vez de usar `getNumber()` (ya existía en `@lib/jid_utils.ts`, solo que casi nadie lo importaba) — antispam, antitoxic, antilink, antitraba, antidelete, antiviewonce, welcome, nsfw, trade, demote y el handler principal. Sin cambio de comportamiento, solo una sola fuente de verdad en vez de 16 copias |
| **`#crime` y `#slut` — cooldowns reducidos** | `#crime` de 1h a 15 min, `#slut` de 1h a 10 min |
| **Descargas de video — caché + deduplicado, mismo remedio que ya tenía el audio** | `#ytvideo`/`#tiktok`/`#ig` no tenían el tratamiento que `#ytmp3`/`#ytaudio` ya tenía desde antes: contenido en tendencia (un TikTok viral, un video que varios mandan a la vez en el mismo grupo) disparaba una descarga+merge de yt-dlp COMPLETA — la operación más pesada de las tres — por cada pedido idéntico. Ahora comparten resultado cacheado (10 min) y descargas en curso idénticas esperan la misma promesa en vez de arrancar la suya |
| **Python — el chequeo de spam de CADA mensaje bloqueaba toda la API** | `/api/v1/spam/check` (llamado en cada mensaje de cada grupo, no solo comandos) llamaba a `check_message()` directo dentro del handler async — con Uvicorn corriendo `--workers 1` (un solo hilo para toda la API), eso bloqueaba ese único hilo en cada mensaje, retrasando en cascada CUALQUIER otro endpoint mientras tanto (patrón ya corregido antes en `fast.py`/`ml.py`, pero que había quedado afuera acá). Movido a `asyncio.to_thread`, mismo patrón que el resto |
| **Python — 5 endpoints más con el mismo problema, auditados de punta a punta** | `/search/image`/`images` (scraping con `requests` síncrono, hasta 10s bloqueado por búsqueda), `/anime/*` (upscale/removebg/tags/detect/restore/convert — procesamiento de imagen real con PIL/torch), `/imagefx/lego`, `/groups/*` (I/O de disco de Parquet), y `/ai/intent/classify` con `use_transformer=true` (carga un pipeline de HF transformers) — ninguno pasaba por `asyncio.to_thread`. Todos corregidos con el mismo patrón |
| **Consola — la caja ASCII completa de cada mensaje se achicó a solo comandos** | El log detallado (`ascii.box`, 6 líneas con bordes y colores) se armaba y se imprimía por CADA mensaje, incluida toda la charla común que no le habla al bot — la inmensa mayoría del volumen en 400+ grupos activos. `console.log` a una consola real de Windows es síncrono, así que esto era trabajo real en el único hilo del event loop de Node por cada mensaje. Ahora la caja completa queda solo para comandos reales; la charla común loguea una línea compacta. Python sigue persistiendo cada mensaje igual (no se pierde trazabilidad) |
| **Fix: el watchdog zombie logueaba una falsa alarma tras cerrarse la conexión** | El ping del watchdog zombie fallando justo después de un cierre de conexión ya no causaba una reconexión duplicada (fix de la 8.6.0) — pero seguía logueando un WARN completo con stacktrace ("Connection Closed") como si fuera un problema aparte, cuando en realidad `requestReconnect()` ya lo ignoraba silenciosamente por dentro. Ahora el watchdog se salta el ping por completo si ya hay una reconexión en curso — mismo resultado, sin el ruido/falsa alarma en los logs |
| **Fix: el respaldo de sesión en Rust (`/write`) abortaba con timeout de 3s** | Mismo bug que ya se había corregido en `/sessions/signal/clear` (8.6.0), pero en otro endpoint: `/write` hace un `fsync()` real por cada respaldo de credenciales, y en Windows con antivirus de por medio eso puede tardar más de 3s — confirmado en vivo con el mismo `AbortError: This operation was aborted`. Subido a 10s, igual que ya tiene `/sessions/signal/clear` con 15s |
| **Investigado: reconexiones "zombie" cada ~10-11 min, todo el día** | Logs reales mostraron el watchdog forzando reconexión cada ~10.5 minutos de corrido, sin relación con tiempo apagado — no es que el bot "tarde en recuperar" tras horas offline, es un ciclo que se repite constantemente. El ping de bajo nivel (`keepAliveIntervalMs`) siempre respondía OK; lo que fallaba era la entrega de mensajes en tiempo real. Hipótesis: `markOnlineOnConnect: false` deja al bot sin señalar presencia nunca, y WhatsApp le baja la prioridad de entrega en tiempo real a una sesión que nunca aparece activa. Agregado un pulso de presencia breve (`available` → `unavailable` a los 8s) cada 5 minutos, para probar la hipótesis sin dejar al número mostrándose "en línea" de forma permanente |

## [8.6.0] — 2026-07-26

Tercera ronda de resistencia en grupos activos, esta vez sobre la causa real de fondo: cada Bad MAC (aunque fuera de un solo grupo) borraba TODAS las sesiones Signal de la cuenta entera, forzando renegociación simultánea en los 400+ grupos y retroalimentando el propio problema. También se cerró la fuga de sockets que quedaba abierta en cada reconexión, y se sumó una colección personal de stickers.

| Área | Cambio |
|------|--------|
| **Fix: Bad MAC — la limpieza de sesiones era global, aunque el problema fuera de un solo grupo** | `clear_signal_sessions` (Rust) borraba **todos** los `session-*.json`/`sender-key-*.json` de la cuenta entera ante CUALQUIER limpieza, sin importar si el umbral que se disparó fue el de un solo grupo. Confirmado en producción: 10 limpiezas "globales" y 11 grupos con limpiezas propias en una sola sesión de 6.5h, con apenas 1 `session-*.json` sobreviviendo pese a 448 grupos activos — un ciclo que se retroalimenta solo (un grupo dispara → se borra TODO → renegociación masiva simultánea → más Bad MAC → repite). Ahora acepta un `groupJid` opcional: con él, borra solo los `sender-key-<grupo>--*.json` de ESE grupo (el JID completo queda embebido en el nombre de archivo que ya usa Baileys); sin él, sigue siendo el borrado global de cuenta completa, reservado para cuando el umbral realmente GLOBAL se dispara. Verificado en vivo con archivos de dos grupos distintos: la limpieza scopeada solo tocó los del grupo objetivo |
| **Fix: reconexión dejaba el socket viejo abierto del lado de WhatsApp** | `cleanup()` quitaba los listeners y soltaba la referencia al socket, pero nunca llamaba a `sock.end()` — cada reconexión (Bad MAC, watchdog zombie, corte de red) dejaba la conexión anterior abierta a nivel de WhatsApp mientras una nueva se abría con las mismas credenciales, justo el patrón que los sistemas antiabuso de WhatsApp están hechos para detectar y castigar con desvinculación forzada. Además, varios puntos del código llamaban `cleanup()` + `scheduleReconnect()` por separado — dos triggers casi simultáneos podían cancelarse el temporizador de reconexión entre sí y dejar el bot sin ningún intento programado. Ambos unificados en un solo `requestReconnect()` guardado; verificado con una reproducción aislada de la máquina de estados (patrón viejo: 0 reconexiones tras dos triggers seguidos; patrón nuevo: exactamente 1) |
| **Fix: precarga completa de grupos se repetía en cada reconexión** | `groupFetchAllParticipating()` (los 448 grupos completos) volvía a correr en CADA reconexión, no solo al arrancar en frío — con reconexiones seguidas, una ráfaga pesada de requests que ya se sospechaba (comentario propio en el código) como posible causa de que WhatsApp empezara a limitar la entrega de mensajes al dispositivo. Ahora se salta si ya se precargó en los últimos 30 minutos — los cambios puntuales de un grupo ya se capturan en vivo por otro lado |
| **Fix: sistema de subida de nivel duplicado ignoraba el toggle `autolevelup`** | `xp.ts` tenía su propia fórmula de nivel y su propio anuncio de subida de nivel, corriendo en paralelo al sistema centralizado de `handler.ts` que sí respeta `autolevelup` — nunca detectado en auditorías anteriores porque vivía en un archivo aparte. Explicaba por qué el aviso de nivel seguía apareciendo con el toggle apagado. `xp.ts` ahora solo suma experiencia; el anuncio corre una sola vez, centralizado |
| **Fix: 2 fugas de memoria reales — cooldowns de `#rw`/`#c`** | `rwCooldowns` y `cCooldowns` guardaban una entrada por cada usuario que alguna vez usó el comando, para siempre — nunca se borraban. Ahora barren entradas vencidas cada 10 minutos |
| **Botones interactivos revertidos en `#pet`** | Los botones nativos (`viewOnceMessage`/`nativeFlowMessage`) agregados para `pet hatch`/`pet info` aparecían como "No se pudo cargar este mensaje" en WhatsApp Web/Desktop — patrón sin uso previo en el resto del bot, nunca confirmado estable. Revertido a los hints de texto plano (`> #comando`) que ya se usan en todo el resto del bot |
| **Nuevo: colección personal de stickers** | `#savesticker` (responder a un sticker para guardarlo con nombre), `#stickers [nombre]` (listar o buscar y reenviar) y `#delsticker` — el `.webp` vive en disco (`data/stickers/<usuario>/`), no en `users.json`, para no engordar ese archivo con binarios |
| **Dragon City — fix de animación del huevo y de los videos de evolución** | Los `.webm` de evolución (fuente en VP9) no se reproducían de forma confiable como video nativo en WhatsApp — aparecían como archivo descargable en vez de loopear. Reencodeados a H.264/MP4 al vuelo con el mismo ffmpeg que ya usa `#sticker`. De paso, se generó una animación real de "huevo temblando" (rotación oscilante sobre la imagen estática) para el momento de incubar, y se corrigió que la etapa 0 (huevo) pudiera quedar guardada como estado de un dragón ya obtenido — nunca debería serlo |
| **`#ytmp3`/`#ytaudio` (+ alias nuevo `#playaudio`) — cola separada, caché y menos tiempo de transcodificación** | Antes competía por los mismos 3 cupos de la cola de descarga de video; ahora tiene su propia cola (4 cupos, tareas más livianas). Pedidos duplicados de la misma canción en un grupo activo (tema en tendencia) ahora comparten una sola descarga en vez de una por persona, con resultado cacheado 15 min. Calidad de audio bajada de la más lenta de codificar (0) a una intermedia (4, ~165-185kbps) — imperceptible por WhatsApp, notablemente más rápida |
| **Rust — resiliencia adicional** | I/O bloqueante restante movida a `spawn_blocking` (`analytics.rs`, `tasks.rs`, apagado ordenado en `main.rs`); runtime `multi_thread` explícito; techo de 30s en cualquier request colgado (`TimeoutLayer`); versión leída de `Cargo.toml` en vez de strings sueltos desincronizados; `db.rs` agrupa múltiples `execute()` de tracking de mensajes en una sola transacción atómica en vez de N autocommits |
| **Rust — logs con rotación real** | El log de arranque crecía sin límite (1.7MB y subiendo). Ahora usa `tracing-appender`: un archivo nuevo por minuto, solo se conservan los últimos 20, escritura a disco en un hilo aparte (no bloquea el hilo que atiende requests) |
| **`ansimax` actualizado a 1.4.10 — tablas ASCII reales** | `scripts/status.js` y `scripts/ai_test.js` migrados a `ascii.table()` en vez de formateo manual con `.padEnd()`. De paso, `ai_test.js` tenía un bug real: nunca mandaba el header `x-api-key` a Rust, así que el test de comparación de NLP fallaba el 100% de las veces en silencio |
| **`#rw` — cooldown bajado a 20 min** | Antes 29 min |
| **Barra de progreso al sincronizar historial** | El evento `messaging-history.set` de Baileys nunca se escuchaba — ahora muestra una barra de progreso en consola durante la sincronización inicial/reconexión, con resumen de chats/mensajes al terminar |

## [8.5.1] — 2026-07-21

Segunda ronda de resistencia — esta vez enfocada en grupos muy activos (10+ personas escribiendo casi al mismo tiempo), donde aparecían Bad MAC con más frecuencia. Se encontraron y corrigieron dos bugs reales que explican buena parte de eso, más mejoras de concurrencia en Rust y el reemplazo completo del sistema de mascotas por Dragon City.

| Área | Cambio |
|------|--------|
| **Fix: mensajes descartados en lote tras una reconexión** | Baileys entrega varios mensajes en un solo evento `messages.upsert` cuando su buffer interno está activo — y ese buffer se activa en **cada reconexión**, no solo al arrancar en frío. El código solo leía `messages[0]`, así que en un grupo activo que sigue hablando justo durante la resincronización (el escenario típico tras un Bad MAC), el resto del lote —comandos, y hasta Bad MAC adicionales del mismo lote— se descartaba en silencio, sin log. Confirmado leyendo el código fuente de Baileys (`event-buffer.js`). Corregido en `socket.ts` y en los sub-bots (`serbot.ts`), ahora se recorre el array completo |
| **Fix: `/nlp/fast` (Rust) entraba en pánico con cualquier texto** | Dos expresiones regulares usaban backreferences (`\1`), sintaxis que el crate `regex` de Rust no soporta por diseño — `Regex::new(...).unwrap()` fallaba la primera vez que llegaba texto no vacío, y por quedar cacheada en un `OnceLock`, volvía a pasar en cada llamada siguiente. En la práctica, la ruta rápida de NLP nunca funcionó. Detectado con `cargo clippy` (lint `invalid_regex`), reescrito sin regex (detección manual de caracteres/patrones repetidos), verificado en vivo sin un solo pánico |
| **Fix: el historial de Bad MAC nunca se guardaba en disco** | `bad_mac.rs` creaba su tabla en una conexión DuckDB separada de la que usan los `INSERT` reales — la tabla quedaba "invisible" para la conexión compartida, y cada intento de persistir un clear fallaba en silencio. Confirmado inspeccionando la base real de producción (solo tenía `conversations`/`user_style`, nunca `bad_mac_events`). Ahora usa la misma conexión compartida para todo |
| **Rust — concurrencia real bajo carga (rate limiter, Bad MAC, locks de sesión)** | `/rate/check` se llama por *cada* mensaje de *cada* usuario — es el camino más caliente del proceso. | Área | Cambio |
|------|--------|
| **Integridad criptográfica** | Directorio auth verificado con Curve25519 `publicFromPrivate` en cada arranque vía `@brashkie/signalis-core` |
| **Recuperación sin QR** | `creds.json` corrupto se restaura automáticamente desde snapshot de Rust — sin escanear QR |
| **Bad MAC por grupo** | Cada grupo tiene su propio contador de ventana deslizante (5 MACs / 30s); un grupo inundado ya no dispara reconexión global |
| **Reconexión infinita** | `maxRetries` eliminado — el bot reconecta para siempre con backoff exponencial máx 64s |
| **Semáforo** | Máximo 25 handlers de mensajes concurrentes — previene agotamiento del event loop bajo flood |
| **Watchdog Rust** | Node.js hace ping a Rust cada 20s; `GET /watchdog/status` devuelve 503 si Node muere |
| **Rate limiter Rust** | 15 msgs / 10s por sender con buckets individuales, sin lock global |
| **AbortController** | Todas las llamadas a la API Rust tienen timeout de 3s — un servidor colgado no acumula Promises pendientes |
| **Soporte Ollama** | IA local (Llama 3, Mistral, etc.) se intenta primero en `_call_ai`, antes de cualquier API cloud |
| **Conteo de snapshots** | Aumentado de 5 → 10 snapshots rotativos por sesión |
| **Aislamiento Python** | `stdio: 'ignore'` evita que el buffer de pipe de 4 KB bloquee el proceso hijo |
| **Fix db.ts** | Eliminado `process.exit(0)` en el handler SIGINT que saltaba el graceful shutdown |
